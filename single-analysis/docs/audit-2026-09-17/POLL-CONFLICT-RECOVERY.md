# getUpdates 409 复发修复

## 观测（上海时间）

凌晨第一版只修复了异常分类、恢复关闭和投递/收取耦合，未处理远端未结束请求。这不是完整的 409 修复。

本次持久化事件顺序：

| 本地读取超时 | 紧随其后的 409 | 间隔 |
| --- | --- | --- |
| 02:05:19 | 02:05:47 | 28 秒 |
| 02:53:53 | 02:54:17 | 24 秒 |

02:54:37 随后出现 ConnectTimeout。两次冲突最终均恢复。修复前服务从 00:44:51 持续运行，NRestarts=0；没有与两次冲突对应的本服务重启。

扩大检查当前进程环境及命令行、/root、/opt、systemd 和脚本配置候选文件（1086 个路径；排除模型认证目录、依赖、运行数据及日志；大于 4MB 文件跳过），只在 /root/single-analysis/.env 找到该凭据。扫描只输出匹配路径或是否匹配，不输出凭据。未发现其他当前本机使用者；这不能证明没有远端或已经退出的使用者。

## 缺陷与因果边界

旧实现将本地 HTTP 超时视作可以重新请求，第一次失败仅退避 5 秒。HTTP 超时不能确认 Telegram 已结束旧请求。两次事件均紧随本地超时，支持延迟旧请求与重试重叠的判断，但历史客户端日志不包含 Telegram 对端请求身份，不能把此判断写成已确认的远端追踪事实。

Telegram 官方 Client.cpp 在新长轮询替换仍存在的 long_poll_query_ 时，对旧请求返回 409；因此“other getUpdates”指另一个请求，不必然是另一进程。Client.h 的 LONG_POLL_MAX_TIMEOUT 为 50 秒：

- https://github.com/tdlib/telegram-bot-api/blob/master/telegram-bot-api/Client.cpp （abort_long_poll / do_get_updates）
- https://github.com/tdlib/telegram-bot-api/blob/master/telegram-bot-api/Client.h （LONG_POLL_MAX_TIMEOUT）

## 修复内容

- 新增 PollingGuard。请求发送前持久化 in_flight 与最晚恢复时间；成功后才清除。超时、取消、HTTP 错误后至少等待 60 秒再发出下一请求，覆盖远端 50 秒长轮询窗口并留 10 秒余量。不能保证覆盖任意长的网络延迟。
- 冷启动等待至少 60 秒排空上一实例的远端请求；崩溃前记录的更晚截止时间继续生效。重启不能绕过恢复等待。
- 轮询 HTTP 读取超时从 35 秒增至 60 秒，25 秒服务端 timeout 保持；总请求限定 90 秒。
- 轮询使用独立连接池。异常后关闭旧轮询连接并重建，不中断发送通知的连接。
- Linux abstract Unix socket 按 Bot ID 哈希绑定进程生命周期的所有权锁；跨工作目录、不同 runtime、PrivateTmp 和 token 轮换仍互斥。锁不输出凭据，进程退出自动释放。此锁只能约束采用该实现且处于相同网络命名空间的实例，不能阻止远端程序。
- 同一 Bot 对象的 offset 读取、请求和提交串行，防止并发调用读到相同旧 offset。
- 失败诊断新增请求序号、起止时间、阶段、恢复截止时间。保留 409 立即告警机制，没有屏蔽复发。

## 验证范围

本地模拟旧请求在客户端超时后继续存活的 Telegram 服务：原来的 5 秒重试落在远端占用期；修复后的请求只在恢复窗口后发出，成功恢复且保持暂停/offset/无新分析。额外覆盖 HTTP 409/502 后重启、取消、崩溃遗留状态、真实子进程所有权互斥、并发 offset、独立连接重建及总超时。

没有用真实 Bot 故意制造冲突，没有额外 getUpdates 探针，没有触发模型或分析，没有改动提示词与信号。
