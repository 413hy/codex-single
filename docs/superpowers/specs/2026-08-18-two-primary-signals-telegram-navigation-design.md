# 固定双主信号、方向质量与 Telegram 导航设计

> 历史专题设计。当前模型、监测、失败与并发语义以 [`2026-08-19-model-centered-signal-system-reliability-design.md`](2026-08-19-model-centered-signal-system-reliability-design.md) 为准；本文件只保留固定双信号与 Telegram 导航的演进记录。

## 1. 目标

系统每个成功的 30 分钟定时周期必须从数据合格候选中选出相对最优的两个主信号，供用户人工判断。主信号必须有明确方向、近端目标、失效条件、形成中 1h 判断和可信度。其余候选只保留内部审计，不作为交易信号通知，也不进入实时监测。

本次同时修复 FHEUSDT 近端方向完全判断相反、WATCH 通知与监测噪声、定时/紧急周期语义混淆、模型永久错误重复通知，以及 Telegram 详情没有返回按钮的问题。

系统继续只使用公开市场数据，不读取账户、余额、仓位，不执行交易。

## 2. 已确认的问题与根因

### 2.1 FHE 方向错误

FHE 16:20 的原始证据已经包含确认高点、5m 转负、距滚动高点约 3.1 ATR 的回撤和明显的 15m 冲击。模型也在文字中承认短线过热和高点回撤，却因为旧 Prompt 先强调 1h/4h 均线与 MACD 背景，把近端衰竭解释成“突破回踩”。17:00 时 15m 已下跌约 8.54%、5m MACD 与方向效率均转负，模型仍保留多头偏向。

因此根因不是行情数据抓错，而是：

1. 预测时域没有严格限定为未来约 30–60 分钟；
2. 高周期背景压过了 15m/5m 近端价格路径；
3. Prompt 没有要求同时比较趋势延续与冲击衰竭；
4. 宿主当时只校验格式和价格几何，没有校验方向与完成 K 线的联合冲突。

上一版通过硬性衰竭规则阻止错向，但规则作用于全部候选，并鼓励把冲突结果降为 WATCH，造成系统过度保守。本次不继续叠加保守门槛。

### 2.2 信号数量不稳定

现有 `max_strong_signals=2`、Schema 和 Prompt 的含义都是“最多两个”，Prompt 还明确禁止凑数，所以成功周期可能产生 0、1 或 2 个 STRONG。这与“每半小时固定给两个相对最优机会”的最终需求不一致。

### 2.3 WATCH 噪声与错误监测范围

通知层在没有 STRONG 时会退化为展示全部结论；有上一轮信号转弱时又会单独展示 WATCH。Prompt 同时要求 WATCH 生成动态阈值，监测器则从所有历史币种的最新结论加载阈值，而不是只读取本轮主信号。已保存的 7 个紧急周期全部由 WATCH 触发并最终仍返回 WATCH，属于低价值调用与通知。

### 2.4 定时周期与紧急周期混淆

`/latest`、MCP 最新信号和健康状态当前可能读取最近一个紧急单币周期，而不是最近一次 30 分钟定时周期。新的“定时固定两个主信号”合同也不能直接套用到单币紧急复核。

### 2.5 模型故障被包装成正常周期

Codex CLI 从上海时间约 05:30 起曾连续出现 workspace credits 耗尽和 401 未登录。编排层捕获错误后，为全部候选创建 `INDETERMINATE` 并照常投递，导致用户收到多轮看似正常、实际没有模型分析的通知。永久性鉴权或额度错误还会在同一周期重复尝试。

### 2.6 Telegram 详情不可返回

当前详情回调会另发一条无 InlineKeyboard 的消息，没有返回本轮结论的入口，也没有使用原消息编辑形成页面式导航。

## 3. 采用方案

采用“分析全部候选，固定选择两个主信号”的方案：

- 正常定时周期有至少两个数据合格候选时，模型必须给出唯一的第一、第二主信号；
- 两个主信号是相对最优机会，不等同于两个绝对强信号；
- 使用 `HIGH / MEDIUM / LOW` 可信度表达质量差异，不用 WATCH 决定是否通知；
- 方向、目标、失效条件和 forming 1h 对两个主信号均为必填；
- 其他候选可以在内部得到 WATCH、NO_STRONG_SIGNAL 或 INDETERMINATE，但不进入正常通知和实时监测；
- 只有数据合格候选少于两个、Codex 调用失败或模型输出连续校验失败时，成功周期才允许少于两个；此时必须发送系统/数据异常，而不是用 WATCH 填充。

不采用“强制两个 STRONG”，因为这会伪造绝对置信度；也不采用程序按扫描分数直接定方向，因为候选排名只表示值得分析，不代表多空。

## 4. 领域合同

### 4.1 周期模式

引入明确周期模式：

- `SCHEDULED`：30 分钟定时批量分析，成功时必须有两个主信号；
- `EMERGENCY`：对某个现有主信号的阈值穿越进行单币复核，只更新该信号状态，不选新的两个主信号。

模式进入持久化模型，不再只藏在 `diagnostics` 或依赖 analysis ID 前缀推断。旧数据库记录缺少模式时，按 ID 前缀兼容解析。

### 4.2 候选评估与选择

每个候选评估增加：

- `selection_rank`: `1`、`2` 或 `null`；
- `confidence`: `HIGH`、`MEDIUM`、`LOW` 或 `null`。

定时模型响应必须满足：

- 所有输入币种各有一个评估；
- 数据合格候选不少于两个时，`selection_rank` 恰好包含且只包含 `1`、`2`；
- 主信号必须有 direction、take_profit、forming_1h、invalidation、evidence IDs 和 1–2 条可支持的监测指令；
- 非主信号的 `selection_rank`、`confidence` 和监测指令必须为空；
- 两个主信号可以同向，不要求人为多空对冲；
- 可信度不参与是否通知，只用于告诉用户两个相对最优机会的质量差异。

为兼容已有 SQLite JSON，新增字段提供空默认值；旧记录仍可查看。`strong_signal_count` 保留为旧数据兼容字段，新周期以 `selected_signal_count` 和 `selected_symbols` 为准。

### 4.3 信号生命周期

上一轮两个主信号与本轮选择比较：

- `NEW`：本轮新入选；
- `MAINTAINED`：继续入选且方向不变；
- `REVERSED`：继续入选但方向改变；
- `EXITED`：本轮未入选且未触及原失效位；
- `INVALIDATED`：已经触及原失效条件。

上一轮落选币只出现在“上轮信号更新”，不算本轮主信号，并立即退出实时监测。

## 5. 方向分析策略

### 5.1 时域与证据优先级

信号方向严格表示未来约 30–60 分钟的近端偏向：

1. 15m 决定当前摆动、区间位置和主要近端路径；
2. 5m 判断加速、回踩/反抽质量、衰竭和反转确认；
3. 1h/4h 只给趋势背景和逆势风险，不得覆盖已经完成的 15m/5m 反向结构；
4. order book、recent trades、OI、funding 和跨所 ticker 只作确认或反证，不替代完成 K 线；
5. 候选排名和涨跌幅大小不得直接决定方向。

### 5.2 双假设比较

每个候选必须比较两个互斥解释：

- 延续假设：当前波动是趋势中的普通回踩/反抽，近端将恢复原方向；
- 衰竭/反转假设：冲击已经失败，完成 K 线开始沿反方向推进。

模型必须依据区间位置、滚动高低点 ATR 距离、确认 pivot 年龄、15m/5m 收益、方向效率、MACD、成交额变化和可用微观证据选择一个近端方向。RSI、EMA 或单个指标不得单独决定结果。

### 5.3 宿主校验边界

宿主只对两个主信号执行联合冲突校验，不再因为内部 WATCH 的方向导致整批重试。校验发现多项完成 K 线与选择方向冲突时：

1. 把具体冲突证据反馈给模型；
2. 要求模型重新比较延续与衰竭，并仍然选择两个相对最优信号；
3. 宿主不直接生成方向，也不自动把结果降成 WATCH；
4. 第二次仍冲突时，本周期按模型输出失败处理，不发送伪信号。

生产规则不包含 FHE、TUT 或其他固定币种名称。FHE 只作为回归样本，TUT/HFT 的正确延续样本用于防止过拟合成“见急涨就做空”。

## 6. 定时与紧急编排

### 6.1 定时周期

流程为：全量扫描 → 深采 Top 5 与上轮两个主信号 → 批量分析 → 校验固定两个选择 → 比较生命周期 → 原子落库 → 单次 Telegram 投递 → 替换实时监测集合。

上一轮主信号即使不在新 Top 5，也要重新采集和分析，供生命周期判断；它不会自动占据本轮两个名额。

### 6.2 紧急周期

紧急周期只允许由当前两个主信号的有效监测指令触发。它使用单币复核合同，回答：

- 原方向是否仍成立；
- 目标或失效条件是否已经改变；
- 是否应标记为 INVALIDATED 并停止监测。

紧急周期不创建新的“本轮两个主信号”，不覆盖最近定时周期、`/latest`、MCP 主信号或下一轮追踪基准。紧急结果使用独立通知标题和投递类型。

## 7. 实时监测

- 监测集合只来自最近成功定时周期的两个主信号；
- 每个主信号最多 1–2 条互补指令，优先失效位和一个确认/目标阈值；
- 非主信号、EXITED、INVALIDATED 和历史残留币种没有活跃指令；
- 紧急复核若确认失效，立即移除该币全部指令；
- 下一次成功定时周期原子替换全部指令；
- 保留迟滞和每小时软预算；最新阈值生命周期以架构重构设计为准：任一指标触发即原子接受首发事件并暂停该币整套旧版本，软预算不吞事件；
- 存储层提供“最近成功定时周期主信号”专用查询，监测器不得再使用所有历史币的 `latest_conclusions()`。

## 8. Telegram 交互

### 8.1 定时通知

每轮只展示：

1. 主信号 1；
2. 主信号 2；
3. 可选的“上轮信号更新”。

主卡包含参考价、方向、可信度、市场状态、唯一目标、forming 1h、失效条件和一段核心解释。不得出现 WATCH 交易信号，也不展示全部候选详情。

上轮 EXITED/INVALIDATED 只作为状态更新，明确写“已退出本轮并停止实时监测”，不伪装成新机会。

### 8.2 详情与返回

定时消息底部为两个“查看分析详情”按钮。点击后：

1. 先 `answerCallbackQuery`；
2. 使用 `editMessageText` 把原消息切换成该币详情；
3. 详情底部显示 `⬅️ 返回本轮信号`；
4. 返回后恢复原本的两个主信号卡和详情按钮；
5. 编辑失败时降级为发送一条带相同导航按钮的新消息。

详情和主页面均限制在 Telegram 文本上限内。InlineKeyboard 编辑不发送 `ReplyKeyboardRemove`，不改变现有 ReplyKeyboard 的展开状态。

`📈 最新信号` 永远读取最近成功的定时周期，不读取紧急周期。`🧭 系统状态` 同时显示最近定时周期、模型健康状态和最近紧急复核时间。

## 9. 存储与 MCP

- cycles 持久化周期模式、成功/失败状态、两个 selected symbols 和 selected count；
- conclusions 持久化 selection rank、confidence 和生命周期状态；
- 新字段采用兼容默认值或轻量迁移，已有历史信号无需删除；
- `get_latest_signals` 返回最近成功定时周期的两个主信号及上轮更新；
- 紧急结果通过独立查询或历史记录访问，不覆盖最新主信号；
- `list_monitoring_directives` 只返回当前两个主信号的活跃阈值；
- MCP 仍保持六个只读工具，不增加账户或交易能力。

## 10. 模型错误与服务降级

Codex 错误分为：

- 永久/人工处理：未登录、401/403、额度耗尽、模型不可用；
- 瞬时：超时、临时网络、非零退出；
- 输出：Schema、证据引用、方向冲突或选择数量校验失败。

处理规则：

- 永久错误本周期不做第二次相同调用；
- 瞬时错误和可修正输出最多按配置重试；
- 模型失败不创建五个 INDETERMINATE 伪结论，不投递正常主信号消息；
- Telegram 只在模型健康状态发生变化时发送一次故障或恢复通知，避免每 30 分钟重复刷屏；
- 数据采集继续运行并记录扫描诊断，系统状态明确显示模型不可用；
- 模型恢复后的第一个成功定时周期正常发送两个主信号。

## 11. 验证与灰盒测试

### 11.1 自动化

- Schema：成功定时响应必须恰好包含 selection rank 1、2；少/重/多均拒绝；
- 主信号完整性：方向、目标、失效、forming 1h、证据和可信度齐全；
- 非主信号隔离：无监测指令、不进入通知；
- 生命周期：维持、反向、退出、触及失效位全部覆盖；
- 存储：紧急周期不能覆盖最近成功定时周期；
- 监测：只有两个主信号订阅，旧币、WATCH 和退出币不残留；
- Telegram：固定两个主卡、退出更新、详情→返回→详情、编辑失败降级、白名单、64-byte callback、幂等；
- 模型错误：credits、401、超时、Schema 和方向冲突分类，状态变化单次通知及恢复；
- 安全：无私有交易端点、Bot Token 不入日志、ReplyKeyboard 参数保持原合同。

### 11.2 历史方向回放

使用冻结证据、禁止未来数据进入输入：

- FHE 16:20：不得继续输出近端多头方向；
- FHE 17:00：不得继续输出近端多头方向；
- TUT/HFT 已验证的趋势延续样本不能被衰竭规则误杀；
- 急跌后反弹使用完全对称样本；
- 保存周期按后续 30m/60m 价格、MFE、MAE、目标/失效先触达进行 walk-forward 统计。

现有可取得后续同币参考价的 13 个历史强信号中约 8 个方向一致，样本少且含连续重复信号，只作为旧版本基线，不作为调参目标。优化必须在固定样本集上比较，不能只为了修好 FHE 而牺牲其他走势。

### 11.3 真实灰盒

1. 真实 Bybit 扫描确认流动性与 Top 5；
2. no-notify 完整周期确认恰好两个主信号；
3. FHE/TUT/HFT 保存证据用真实 Codex 回放；
4. 正式 Telegram 周期确认两个主卡、详情和返回；
5. 造一个当前主信号阈值穿越，确认只触发单币紧急复核且不污染 `/latest`；
6. 模拟 Codex 401/credits 后恢复，确认只发送一次故障和一次恢复；
7. MCP 六工具实机调用，确认最新主信号和监测范围一致；
8. 重启服务并观察下一个墙钟整点/半点周期、单实例锁、日志和投递幂等。

所有失败场景必须修复并重跑，不能把单元测试通过当作部署完成。

## 12. 发布与回滚

实现后先运行自动化与 no-notify 灰盒，再停止旧单实例服务、提交可回滚版本并启动新服务。首个正式周期若未输出两个主信号、仍通知 WATCH、监测集合超过两个币、Telegram 返回失败或模型错误被包装成正常信号，则立即停止新版本并恢复上一提交与配置；SQLite 历史数据保留。

## 13. 非目标

- 不增加自动下单、仓位、余额、杠杆或账户 API；
- 不保证每个信号盈利；
- 不用固定币种名单决定方向；
- 不通过无限提高置信门槛追求表面稳定；
- 不把扫描排名当作方向或买卖建议。
