# 多周期 K 线预测设计

日期：2026-08-18  
状态：用户已确认，已部署并通过灰盒验证

## 1. 目标与边界

系统在每次成功的 30 分钟定时分析中，继续恰好发送两条相对最优主信号，并为每条主信号补充四个简洁的 K 线方向预测：

1. 形成中 15m；
2. 形成中 30m；
3. 形成中 1h；
4. 下一根完整 15m。

紧急复核通知也输出同样四项。内部未入选币不强制生成这些预测，避免扩大模型输出、制造无意义预测或干扰主信号相对比较。

预测服务于约 15～60 分钟的人工超短线判断。系统不读取或输出账户、仓位、保证金、杠杆、数量、下单动作、止损金额或收益承诺。模型只根据公开市场结构给出方向参考。

## 2. 方案选择

采用“下一根 15m”，不采用“下一根 30m”。下一根 15m 与超短线判断更贴合，且不会与形成中 30m 大量重叠。四项预测均只输出：

- 唯一方向：`LONG_BIAS` 或 `SHORT_BIAS`；
- 强度：`WEAK`、`NORMAL` 或 `STRONG`；
- 明确的 UTC 时间窗，由宿主转换为上海时间；
- 简洁依据，详情页展示，主通知不展开。

不预测精确开、高、低、收价格，避免在高波动山寨币上制造虚假精度。已有唯一近端目标位和方向失效条件保持不变。

## 3. 数据与证据

原生行情采集新增已完成 30m K 线，并与现有 5m、15m、1h、4h 一样经过以下校验：

- 只使用完成柱；
- 时间连续性和缺口检查；
- OHLC 一致性检查；
- 指标、确认 pivot、rolling range、ATR、成交量与成交额均从对应完成柱计算；
- 数据缺失按字段降级，不填零，不用其他交易所覆盖 Bybit 参考价。

模型输入包含真实的已完成 5m、15m、30m、1h、4h 证据和当前 Bybit last/mark。四项预测是本轮输出，不能在同一轮反过来充当行情证据，防止模型用自己的预测证明自己的方向。

## 4. 时间窗合同

宿主按分析请求时刻计算并提供四个不可自行改写的窗口：

- 形成中 15m：请求时刻所在的自然 15 分钟窗口；
- 形成中 30m：请求时刻所在的自然半小时窗口；
- 形成中 1h：请求时刻所在的自然小时窗口；
- 下一根 15m：紧接形成中 15m 之后的完整自然 15 分钟窗口。

窗口使用左闭右开语义。例如请求时间为上海时间 10:32，则四个窗口分别是 10:30～10:44、10:30～10:59、10:00～10:59 和 10:45～10:59。Schema 中以 UTC 的 `window_start` 和 `window_end` 表示，界面以分钟显示时将结束边界减一分钟呈现。

若模型返回的窗口与宿主提供值不完全一致，整份输出校验失败并进入有限重试。若分析耗时跨过窗口边界，通知明确标注“分析时”，不把旧窗口冒充发送时仍在形成的 K 线。

## 5. 模型合同与分析方式

领域模型新增通用 `CandleOutlook`，主信号必须包含：

- `forming_15m`；
- `forming_30m`；
- `forming_1h`；
- `next_15m`。

四项必须各有方向、强度、窗口和依据。非主信号允许全部为 `null`，且不得带实时监测指令。紧急复核必须重新生成四项，但不产生新的定时 selection rank。

Prompt 要求模型先根据完成 5m/15m/30m 结构判断形成中 15m 与下一根 15m，再用 30m、1h、4h 背景判断形成中 30m 和 1h。不同周期允许方向不一致；这种不一致是市场结构信息，不通过机械投票合成方向。最终主信号方向仍代表未来约 30～60 分钟的综合近端偏向。

宿主校验以下内容：

- 两个定时主信号和紧急复核结论均具备四项预测；
- 非主信号没有四项预测；
- 每个窗口边界与本轮输入完全一致；
- 预测方向和强度只能使用枚举值；
- forming 15m、30m、1h 与 next 15m 的窗口身份不混淆。

## 6. Telegram 展示

每条主信号卡在市场状态之后显示四行：

```text
形成中 15m（分析时）：偏空 / 一般 · 10:30–10:44
形成中 30m（分析时）：偏空 / 较强 · 10:30–10:59
形成中 1h（分析时）：偏多 / 较弱 · 10:00–10:59
下一根 15m：偏空 / 一般 · 10:45–10:59
```

主通知只保留方向、强度和窗口。每项依据放入“查看分析详情”。详情页继续提供“返回本轮信号”内嵌按钮；ReplyKeyboard 配置和不移除键盘的约束不变。

如果 Telegram 长度接近限制，优先压缩详情中的工具状态与证据 ID 展示，不删除两条主信号的四项预测、目标或失效条件。HTML 截断必须保持标签有效。

## 7. 存储、监测与 MCP

SQLite 继续保存完整周期 JSON，不新增必须迁移的关系字段。读取旧周期时，缺少新预测字段仍可兼容；只有新合同版本的成功周期才强制四项齐全。

实时监测仍只加载最近成功定时周期的两个主信号阈值。预测不会自动变成阈值，也不会因每个周期方向变化而额外唤醒模型。

MCP 的最新信号与详情返回四项预测；健康接口不因新增预测改变含义。所有 MCP 能力继续保持只读。

## 8. 故障处理

- 30m K 线采集失败但 5m/15m/1h 可用时，保留币种证据并标记 30m 字段不可用；模型不得把缺失当作零。
- 若入选主信号无法生成四项合法预测，本轮视为模型输出失败，不用 WATCH、候选排名或旧预测填充。
- 永久模型错误继续单次失败并去重通知；恢复后再发送正常的两条主信号。
- 旧成功周期仍可由 `/latest` 和 MCP 读取，但界面只展示其实际具备的旧字段，不伪造 15m/30m 预测。

## 9. 验证标准

自动化测试必须覆盖：

1. 15m、30m、1h 与下一根 15m 窗口边界，包括整点、半点和跨日；
2. 新周期两个主信号和紧急复核均具备四项预测；
3. 非主信号不含预测和监测指令；
4. 缺少字段、窗口错位、方向或强度非法时模型输出被拒绝；
5. 30m 完成柱采集、证据构建和数据降级；
6. Telegram 主通知四行完整、详情可返回、HTML 长度安全；
7. 旧 SQLite 周期向后兼容；
8. FHE 历史证据回放不恢复成错误近端多向；
9. 真实 Bybit no-notify 周期恰好两条主信号，四项时间窗与方向均可解释；
10. 正式 Telegram、MCP、实时监测和下一墙钟周期灰盒通过。

## 10. 验收结果

功能完成时，用户每 30 分钟收到恰好两条主信号，每条同时包含形成中 15m、形成中 30m、形成中 1h 和下一根 15m 的简洁预测；退出币只作为状态更新，内部 WATCH 不通知，实时监测只服务当前两条主信号。
